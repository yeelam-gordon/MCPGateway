شارك خدمات MCP الخلفية المحلية بين الجلسات: تجنّب تكرار الذاكرة، واستخدم الخدمات التي تعمل بالفعل، وأضف خدمات عبر الإعدادات مع إبقاء اتصال MCP الحالي للوكيل دون إعادة تشغيله (SDK/stdio؛ صافي الفائدة يعتمد على الاستهلاك الإضافي).

[ابدأ عبر Copilot CLI](#first-use) · [تحقق العملاء](../CLIENTS.md#compatibility-summary) · [الأدلة](#resource-examples)

<img src="../../assets/mcp-gateway-benefits.png" alt="أعِد استخدام عملية الخادم بدل تشغيل نسخ تستهلك ذاكرة إضافية لكل جلسة." width="780">

رسم مفاهيمي بعناوين إنجليزية، وليس لقطة تشغيل أو اختبار أداء.

- **تجنّب تكرار ذاكرة الخدمات الخلفية:** مثال افتراضي: 5 × 1.5 GB → مجموعة واحدة؛ تجنّب تكرار 6 GB **قبل** استهلاك البوابة والموصّلات الإضافي، وليس توفيرًا مقاسًا.
- **أعِد استخدام عمل بدء التشغيل المتكرر:** إذا استخدمت الجلسات الخمس خدمات stdio الـ12 كلها: 60 → 12 عملية بدء، وليس بدءًا أسرع بنسبة 80%.
- **أضف الإعدادات فقط؛ احتفظ باتصال الوكيل:** SDK/stdio: تبقى تهيئة واحدة (1) بعد انتهاء العمل وإعادة تشغيل البوابة المملوكة؛ يبقى الموصّل نشطًا. لا يطبّق تغييرات الإعدادات تلقائيًا دون إعادة تشغيل (hot reload)، وليس تحققًا من واجهة محادثة أصلية. قد يتطلب التسجيل الأول أو ترقية بيئة التشغيل إعادة تشغيل العميل. [SDK/stdio](../BENCHMARK.md#configuration-only-connection-continuity)

مناسب لعدة جلسات تستخدم الخدمات والكتالوج نفسيهما؛ قد لا تبرر جلسة واحدة أو خدمات خفيفة الاستهلاك الإضافي.

<a id="first-use"></a>
## الإعداد والاستدعاء الأول

**المتطلبات:** Node.js 24 أو أحدث، وnpm، وGit، وCopilot CLI مع الإضافات، وخدمات MCP مهيأة ومصادق عليها مسبقًا. يمر التثبيت الأول حاليًا عبر Copilot CLI؛ Windows منصة الاختبار الرئيسية وAgency اختياري. تختلف مستويات التوافق والتحقق بين العملاء.

قد تحتوي الإعدادات والنسخ الاحتياطية على بيانات اعتماد؛ أبقها خاصة ووافق على التغييرات المقصودة فقط.

[الخروج وبيئة التشغيل المستمرة](../REFERENCE.md#planned-exit) · [استعادة الإعدادات لا توقف عملية البوابة المستمرة (rollback ≠ daemon shutdown)](../REFERENCE.md#setup-recovery)

```powershell
copilot plugin marketplace add yeelam-gordon/MCPGateway
copilot plugin install shared-mcp-gateway@mcp-gateway
```

1. بعد التثبيت افتح Copilot CLI واستدعِ `/mcp-gateway-setup`. راجع المعاينة قبل الموافقة على التغييرات المطلوبة فقط. أغلق Copilot ثم أعد فتحه ونفّذ `readinessCommand` الدقيق الذي أعاده الإعداد. احتفظ بالنسخ الاحتياطية الخاصة وأوامر التراجع.

`readinessCommand` هو الكائن الذي أعاده الإعداد، وليس سلسلة نصية لأمر يُنفَّذ في مفسّر الأوامر (shell). عيّن `$readinessCommand` إلى ذلك الكائن نفسه من نتيجة الإعداد الموافق عليه، ثم نفّذ مثال PowerShell. يحفظ `.command` مسار الملف التنفيذي ويحفظ `.args` جميع الوسائط بالترتيب، بما فيها المسارات ذات المسافات أو علامات الاقتباس. لا تدمج المصفوفة ولا تخمّن المسارات. الفحص لا يبدأ بوابة غير مشغلة.

احفظ فقط كائن JSON باسم `readinessCommand` من نتيجة الإعداد الموافق عليه، لا المخرجات كلها، في ملف UTF-8 باسم `readiness-command.json` داخل المجلد الحالي الخاص. أبقِ `.command` المعروف والموافق عليه وجميع `.args` كما هي؛ لا تدمج الوسائط ولا تخمّن المسارات. حلّل JSON الإعداد هذا فقط، لا بيانات ويب أو خدمات عشوائية؛ تحليل JSON ليس تقييمًا للشيفرة. أبقِ الملف خاصًا لأن محتوى الوسائط يعتمد على الإعداد.

```powershell
$readinessCommand = Get-Content -Raw -LiteralPath '.\readiness-command.json' | ConvertFrom-Json
$command = $readinessCommand.command
$commandArgs = @($readinessCommand.args)
& $command @commandArgs
```

لا يتطلب الاكتشاف والمخطط حجزًا؛ إذا كان `requiresExclusiveAccess: true`، يجب استخدام `claim_server` قبل `call_tool`.

> استخدم البوابة في [مهمة القراءة المأذون بها]: اعرض الخوادم، وابحث عن الأداة وافحص مخططها، وجهّز الوسائط بقيم اختبار مأذون بها وغير حساسة. احصل على الموافقات المعتادة، واحجز قبل التنفيذ الحصري وحرّر بعد اكتمال جميع الاستدعاءات. أظهر النتيجة الفعلية. لا تكرر نتيجة مجهولة؛ سلّم الحالة إلى مسؤول التثبيت.

[SDK tool flow: `list_servers` → `search_tools` → `get_tool_schema` → `claim_server` (exclusive) → `call_tool` → `release_server`](../../README.md#first-use) · [REFERENCE](../REFERENCE.md#unknown-exclusive-result)

2. استدعِ `list_servers` مع `{}`: يُفترض ظهور الأسماء المستعارة والحالات ومؤشرات الوصول الحصري للخدمات المهيأة. اختر خدمة خلفية مأذونًا بها، وابحث عن مصطلح يناسب المهمة باستخدام `search_tools`، ثم اطلب مخطط إدخال الأداة عبر `get_tool_schema`. جهّز الوسائط وفق المخطط واستخدم `call_tool` لتنفيذ قراءة معتمدة. النتيجة المتوقعة سجل فعلي أو نتيجة فارغة موضحة؛ افحص الأخطاء أيضًا، فمجرد وصول رد لا يثبت النجاح.
3. إذا كان `requiresExclusiveAccess: true`، استخدم `claim_server` قبل الاستدعاء و`release_server` بعد انتهاء جميع الاستدعاءات. لا تحتاج الخدمات غير الحصرية إلى حجز. لا تعاود المحاولة عند انتهاء المهلة مع نتيجة مجهولة؛ راجع العمل الجاري ونسّق إعادة التشغيل. إذا كانت النتيجة مجهولة، تبقى الخدمة الخلفية ذات الوصول الحصري محظورة حتى إعادة تشغيل البوابة؛ تحرير الحجز أو فصل العميل لا يرفع الحظر بأمان، وفصل الاتصال لا يلغي العملية.
4. في جلسة ثانية تستخدم الموصّل والكتالوج نفسيهما، كرر `list_servers` / `search_tools` للاسم المستعار نفسه. يُتوقع `ready` للخدمة المهيأة وقدرات من الكتالوج نفسه. تطابق الاسم لا يثبت هوية العملية أو توفير RAM؛ راجع اختبار المشاركة العام. [طريقة مشاركة العمليات](../BENCHMARK.md#method) · [اختبار ذاكرة الكتالوج](../../test/catalog-scale.test.js)

## الحدود والخصوصية والاستعادة

العثور على هذا المستودع عبر Claude Code أو Codex أو Gemini CLI أو Kimi أو Qwen CLI لا يضمن التكامل المباشر مع العميل. لا يوجد مسار تثبيت موثق لـ Gemini CLI هنا؛ Antigravity عميل آخر. اختُبر Kimi على مستوى المهايئ فقط. قد تحتوي الإعدادات والنسخ الاحتياطية على بيانات اعتماد؛ لا تنشرها ولا تضفها إلى التحكم في الإصدارات. قد تتصل الخدمات الخلفية بخدمات بعيدة؛ المشاركة لا تعني العمل دون اتصال ولا تضمن توفيرًا ثابتًا في RAM أو رموز النموذج (tokens).

إذا كانت القائمة فارغة، تحقق من الإعداد المحدد ومعاينة الترحيل. إن لم تجد أدوات، استخدم كلمات من وصف الخدمة الخلفية. عند فشل المصادقة أو الجاهزية اتبع المرجع التشغيلي، ولا تبدأ عملية موازية لتجاوز البوابة. استعادة إعداد العميل لا توقف بيئة التشغيل المستمرة؛ عند التوقف عن الاستخدام راجع تسليم الطلب للمشغّل وفحوص الإتمام.

**قلّل استهلاك الذاكرة الناتج عن تكرار الخدمات الخلفية**

افتراض توضيحي، وليس اختبار أداء: تحتاج كل جلسة من 5 جلسات إلى الاتصالات الـ12 نفسها؛ وتستخدم مجموعة كاملة من الخدمات الخلفية 1.5 GB. تتشارك الجلسات المتوافقة العمليات الفعلية عبر الموصّل والكتالوج نفسيهما.

| النشر | RAM للخدمات الخلفية |
|---|---|
| نسخ مستقلة | 5 × 1.5 GB = 7.5 GB |
| مجموعة مشتركة | 1.5 GB + الاستهلاك الإضافي للبوابة والموصّلات |

RAM المكررة التي يمكن تجنبها قبل الاستهلاك الإضافي: 7.5 GB - 1.5 GB = 6 GB. إجمالي التوفير مجهول حتى القياس. ليست 1.5 GB قيمة ثابتة لكل حمل عمل أو عميل؛ ولا يعني ذلك توفير RAM لخمسة نماذج.

**أعِد استخدام عمل بدء التشغيل أيضًا.** إذا استخدمت الجلسات الخمس جميع خدمات stdio الـ12، تتطلب النسخ المستقلة حتى `5 × 12 = 60` عملية بدء مقابل `12` للمجموعة المشتركة: تجنّب `60 - 12 = 48` عملية مكررة، أي `48 / 60 × 100 = 80%` أقل. يُوصَل فقط ما يُستخدم من الخدمات وعدده `k` عند الحاجة؛ ولا تبدأ الخدمات غير المستخدمة. هذا عدد عمليات، لا بدء أسرع بنسبة 80%. لم يُقَس التأخير؛ التزامن والمصادقة والمنصة تؤثر في الزمن.

1000 أداة → 6 تعريفات أولية: (1000 - 6) / 1000 × 100 = 99.4% أقل في عدد التعريفات، لا في الرموز النصية (tokens). للمخططات المطلوبة لاحقًا تكلفة أيضًا؛ وقد تكون الفائدة أقل للعملاء الذين يؤجلون التحميل أصلًا. يتحقق اختبار الكتالوج الاصطناعي من ست أدوات وذاكرة اكتشاف مشتركة بين عميلين، وليس من أداء RSS. [catalog-scale.test.js](../../test/catalog-scale.test.js)

**قياس تجهيز خفيف: زاد مجموع working set للعمليات** القيمة الوسيطة لثلاث تجارب، Windows x64 / Node 24.13.1: المخطط + echo المشترك 426.2 ms لخدمة خلفية باردة، 21.1 ms للعميل الثاني، 19.0 ms للخامس. إجمالي العميل الأول: مباشر 503.5 ms، مشترك مع بوابة جاهزة 894.3 ms؛ البدء المشترك البارد بالكامل 1886.7 ms. عمليات الخدمات الخلفية 5 → 1، لكن جميع العمليات 5 → 7 ومجموع working set من 357.0 MiB → 564.0 MiB: مجموع working set للعمليات أعلى؛ لم تُقَس الذاكرة الفعلية الفريدة. أداة echo واحدة لا تمثل الخدمات الفعلية الثقيلة؛ و1.5 GB أعلاه افتراض منفصل، لا قياس. [BENCHMARK.md](../BENCHMARK.md)

المقاس هو مجموع working set للعمليات؛ لم تُقَس الذاكرة الفعلية دون العد المكرر ولا البايتات الخاصة (private bytes).

## آلية العمل

أضف خدمات خلفية دون إعادة تشغيل اتصال MCP الحالي للوكيل: زامن الإضافات، وأنهِ العمل الجاري، ثم أعد تشغيل البوابة المملوكة فقط؛ يعيد الموصّل الحالي الاتصال. [SDK/stdio](../BENCHMARK.md#configuration-only-connection-continuity)

يحافظ اختبار SDK/stdio على الموصّل واتصال MCP نفسيهما لاكتشاف اسم مستعار جديد وتنفيذ echo بعد إعادة التشغيل؛ لم تُختبر واجهات المحادثة الخاصة بالمنتجات. لا يطبّق تغييرات الإعدادات تلقائيًا دون إعادة تشغيل (hot reload)؛ التعارضات تحتاج مراجعة. قد يتطلب التسجيل الأول أو ترقية بيئة التشغيل إعادة تشغيل العميل. لا تُعاد الاستدعاءات المنقطعة؛ أعد حجز الوصول الحصري بعد إعادة التشغيل.

هذه ليست منصة حوكمة API للمؤسسات.

تعرض البوابة دائمًا 6 أدوات للوكيل: 4 لاكتشاف القدرات واستدعائها، و2 لعمليات التكامل التي تحتاج إلى سير عمل حصري. لا تؤدي إضافة الاتصالات إلى تكبير الواجهة الأولية؛ ولا يُحمّل المخطط الكامل إلا للأداة المختارة. تُعاد الاستفادة من الاتصالات التي أعددتها وصادقت عليها، من دون تثبيت خدمات أو توفير بيانات اعتماد.

```text
وكيل A ─┐                     ┌─ تكامل A: أدوات متعددة
وكيل B ─┼─ موصّل ─ MCPGateway ─┼─ تكامل B: أدوات متعددة
وكيل C ─┘                     └─ تكامل C: أدوات متعددة
```

يصل عدة وكلاء إلى MCPGateway عبر الموصّل نفسه، ويُنشأ الاتصال بالخدمات الخلفية المُعدّة والمختارة عند الحاجة. يوضح الرسم آلية المشاركة؛ وليس اختبار أداء أو دليلًا على التشغيل الفعلي، ولا يعني بدء تشغيل جميع الخدمات الخلفية.
